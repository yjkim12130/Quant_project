# 시장환경 지표 명세 v1 (market_context_spec_v1)

> 2026-08-15 브레인스토밍 세션에서 확정. 공급·교통·자산군비교 3개 지표를 **조회용 신규/확장 탭**으로 추가.
> 스코어링(`rv_z` 등)에는 반영하지 않음 — 향후 통합 여부는 §6 참고.
> 전제: 6팩터 스코어링(`docs/algo_spec_v1.md`)·레짐(`docs/regime_spec_v1.md`)은 이 문서로 변경되지 않음.

## 0. 배경 및 범위

기존 스크리너는 단지 내부 데이터(그룹 대비 괴리율)만으로 저평가를 판단한다. 여기에 사용자가 직접
확인하고 싶어하는 세 가지 "시장 맥락" 정보를 추가한다:

1. **공급**: 수도권 향후 입주물량(분양+정비사업)
2. **교통**: 단지에서 강남·종로·여의도·판교·동탄까지 출퇴근 소요시간
3. **자산군 비교**: 나스닥·코스피·금·비트코인 대비 부동산의 상대적 저평가 정도

세 지표 모두 **의사결정 참고용 조회 화면**이며, 스크리너의 하드필터/스코어에 자동 반영하지 않는다
(수동 큐레이션 데이터의 신뢰도가 아직 검증되지 않았고, 사용자가 직접 눈으로 판단하고 싶어함 — 2026-08-15 확정).

## 1. 최종 탭 구성

```
📖 가이드 | ⏱️ 매수 타이밍 | 🌐 자산 비교(확장) | 🏗️ 공급(신규) | 🚇 교통(신규) | 🔍 스크리너 | 🏢 단지 상세(교통 추가) | 🧪 백테스트
```

## 2. 공급 지표 (🏗️, 신규 탭)

### 2.1 데이터 소스
- **분양 예정(자동)**: 청약홈 API(data.go.kr) — 지역별 향후 분양 일정·세대수. `ingest/fetch_supply.py` 신규.
- **정비사업(수동)**: 재개발/재건축은 구조화 API가 없음(2026-08-14 조사에서 T3 확인됨).
  `config/manual_catalysts.yaml`의 `redevelopment:` 섹션에 주요 대단지(기준: 1천 세대 이상)만 수동 등록.
  필드: `region_code, complex_name, stage(조합설립/관리처분/이주철거/착공/준공), expected_units, expected_year`

### 2.2 집계 및 저장
- 집계 단위: `config/regions.yaml`의 30개 시군구 코드(법정동코드 5자리)와 동일 레벨.
- 신규 테이블: `supply_presale(region_code, expected_ym, project_name, total_units, source)`
- 정비사업분은 별도 테이블 없이 YAML에서 실행 시점에 로드(변경 빈도 낮음, 정규 ingest 불필요).

### 2.3 화면
- 시군구별 향후 3년 연도별 스택 막대그래프 (분양 vs 정비사업 색 구분).
- 참고선: 최근 5년 평균 입주량 — 배수로 "공급 과다/부족" 직관 제공.
- 지역×연도 물량 표(다운로드 가능하면 좋음, v1 필수 아님).

## 3. 교통 지표 (🚇, 신규 탭 + 단지 상세 필수 반영)

### 3.1 좌표 확보
- 카카오로컬 API로 단지(`apt_seq` 고유값, 수천 건) 주소→좌표 지오코딩.
- `ingest/fetch_geocode.py` 신규, 일회성 배치 + 신규 단지 발생 시 재실행.
- 신규 테이블: `complex_coords(apt_seq, lat, lon, geocoded_at)`

### 3.2 역-역 소요시간 그래프
- 공공교통공단(TAGO) 노선도·역위치 데이터로 역 그래프 구성 (평균 역간 소요시간 ~2분/역 + 환승 페널티).
- `ingest/fetch_transit.py` 신규.
- 신규 테이블: `station_graph(station_id, line, lat, lon)`, `station_edge(from_id, to_id, minutes)`

### 3.3 소요시간 산출
- 단지 좌표 → 최근접역 매칭 → 5개 업무지구 대표역(강남역/종각역/여의도역/판교역/동탄역)까지 최단경로 계산.
- 신규 테이블: `complex_transit_time(apt_seq, dest(강남/종로/여의도/판교/동탄), minutes, calculated_at)`

### 3.4 예정 노선 (착공/준공)
- `manual_catalysts.yaml`의 `transit_planned:` 섹션에 GTX 등 착공/준공 예정 노선 수동 등록.
  필드: `line_name, stations[], stage(착공/공사중/준공예정), expected_open_year`
- 개통 전 노선은 "예정" 배지로 별도 표시. **현재 소요시간 계산(3.3)에는 포함하지 않고 별도 컬럼**으로만
  참고 노출 (확정치와 예정치 혼동 방지 — 2026-08-15 확정 원칙).
- 개통연도가 가까울수록(3년 이내) 목록 상단에 노출하는 정도의 가중만 적용, 소요시간 수치 자체는 변경하지 않음.

### 3.5 화면
- 신규 탭: 지역(시군구) 선택 → 대표 좌표 기준 5개 업무지구 소요시간 표/막대 + 예정노선 배지.
- **단지 상세 탭(tab2)**: 선택한 단지의 5개 업무지구 소요시간을 필수 표시 (2026-08-15 사용자 확정 — 생략 불가).

## 4. 자산군 비교 확장 (🌐, 기존 tabA)

기존 tabA(리베이스 차트 + 기간별 수익률표 + 모멘텀 순위)는 **그대로 유지**한다
(사용자 확인: YJalgo 스타일과 동일 패턴이라 변경 불필요, 2026-08-15).

추가하는 것은 "저평가 정도를 숫자로" 보여주는 z-score 카드뿐:

```
ratio(asset, t)   = reb_apt_index(t) / asset(t)          # asset ∈ {나스닥, 코스피, 금, 비트코인}
ratio_z(asset, t) = ( ratio(t) - mean(ratio, 전체 역사) ) / std(ratio, 전체 역사)
```

- 룩백: R-ONE 데이터 시작 시점(2003~) 전체 역사. 기존 `rv_z`와 같은 "자기 역사 대비 z-score" 프레임 재사용.
- 표시: 리베이스 차트 상단에 4개 metric 카드 (예: "🏠/🇺🇸 -1.2σ"), 음수 = 부동산이 해당 자산 대비
  역사적으로 싸다 (기존 rv_z "낮을수록 저평가" 판정 언어와 통일).
- 계산 위치: `scoring/` 내 신규 함수 (기존 `load_assets()` 반환 데이터프레임 사용, 신규 ingest 불필요).

## 5. 공통 아키텍처

### 5.1 신규 파일
| 파일 | 역할 |
|---|---|
| `ingest/fetch_supply.py` | 청약홈 분양 예정분 적재 |
| `ingest/fetch_geocode.py` | 카카오로컬 단지 좌표 지오코딩 |
| `ingest/fetch_transit.py` | TAGO 노선도 적재 + 역간 최단경로 계산 |
| `config/manual_catalysts.yaml` | 정비사업(공급) + 예정노선(교통) 수동 큐레이션, 섹션 분리 |
| `scoring/asset_zscore.py` (또는 기존 파일에 함수 추가) | 자산군 비율 z-score 계산 |

### 5.2 신규 API 키 (`config/api_keys.local.yaml`에 추가)
- 청약홈 (data.go.kr 내 별도 서비스)
- 카카오로컬 (카카오 디벨로퍼스)
- 공공교통공단 TAGO (data.go.kr)

### 5.3 DB
- 기존 `data/realestate.db`에 테이블만 추가 (신규 DB 파일 아님): `supply_presale`, `complex_coords`,
  `station_graph`, `station_edge`, `complex_transit_time`

### 5.4 캐싱/갱신 정책
- 지오코딩·역간거리그래프: 정적에 가까움 → 배치 1회 + 수동 재실행 (신규 단지/노선 개편 시).
- 청약홈 분양 예정: 월 1회 정도 수동 트리거 (기존 ingest 패턴과 동일, 자동 스케줄 없음).

## 6. 향후 확장 (v1 범위 밖, 참고용)

- 공급압력을 스코어링 Factor6(공급압력)으로 승격하는 것은 `docs/algo_spec_v1.md` §3 Factor6에 이미
  자리가 예약되어 있음 — 이 문서의 `supply_presale` 테이블이 그 데이터 소스 후보가 됨. v1은 조회만.
- 교통 소요시간을 레짐/스코어에 넣는 것도 v1 범위 밖. 데이터 신뢰도(카카오 지오코딩 정확도, 역간
  평균시간 근사의 오차 ±5~10분)를 실측한 뒤 판단.

## 7. 구현 순서 (제안)

1. 지오코딩(`fetch_geocode.py`) — 다른 두 지표보다 선행 필요 없지만, 단지 상세 탭 필수 반영이 걸려있어 우선순위 높음
2. 교통(`fetch_transit.py` + `complex_transit_time` 계산) → 단지 상세 탭 반영
3. 공급(`fetch_supply.py` + `manual_catalysts.yaml` 정비사업 섹션) → 신규 탭
4. 교통 예정노선(`manual_catalysts.yaml` transit_planned 섹션) → 교통 탭 배지
5. 자산군 z-score → tabA 확장 (가장 간단, 신규 ingest 불필요)

각 단계는 API 키 발급 가능성 확인(스파이크)이 선행되어야 함 — 청약홈/카카오로컬/TAGO 키 신청 및
엔드포인트 검증.
